# 03.8 算子融合何时减少实际开销

矩阵乘法、偏置、激活和归一化可以写成多个独立算子，也可以在一次计算内连续完成。算子融合（operator fusion）把相邻计算放进更少的执行入口或计算核，主要减少中间结果写回、再次读取和计算核启动。它改变执行组织，不改变公式定义和输出语义。

## 三个容易混淆的层次

| 层次 | 改变什么 | 示例 |
| --- | --- | --- |
| 请求组批 | 选择哪些请求在同一步执行 | Chapter08 同时选择两个 Decode 请求 |
| 张量打包 | 把多行输入组织成共同张量 | 将两个请求的词元行组成 `[B*T,D]` |
| 算子融合 | 在一次执行中连续完成相邻运算 | 反量化、点积和归约放进一个量化 GEMV 计算核 |

请求组批提供共享计算的机会，张量打包提供连续数据布局，算子融合才减少算子边界。完成前两项并不意味着已经融合，也不保证端到端更快。

## 融合怎样节省时间

假设两个算子先产生中间张量 `Z`，再从 `Z` 计算输出：

```text
unfused: X -> kernel A -> Z in global memory -> kernel B -> Y
fused:   X -> one kernel keeps Z in registers/shared memory -> Y
```

融合可能减少三类成本：

1. 中间张量的全局内存写入和读取。
2. Host 提交计算核以及设备调度计算核的次数。
3. 多次遍历相同权重、索引或缩放参数的开销。

收益取决于负载。中间张量很小、计算核本身很重或成熟库实现明显更快时，融合节省的边界成本可能不足以抵消新实现的代价。

## 为什么融合也可能变慢

融合后的计算核通常承担更多状态。寄存器或共享内存增加会降低活跃线程束数量；额外分支和同步会增加停顿；为多种 shape 编写的通用融合核也可能失去专用库计算核的效率。融合还会扩大错误回滚和数值对照范围。

因此需要同时检查：

| 检查项 | 要回答的问题 |
| --- | --- |
| 公式与顺序 | 浮点运算顺序变化是否仍在容差内 |
| 中间状态 | 中间值能否留在寄存器或共享内存，而不是换一种方式写回显存 |
| 资源占用 | 寄存器、共享内存和线程块配置是否降低占用率 |
| 启动次数 | 融合是否实际减少了计算核实例数 |
| 端到端结果 | 减少局部时间后，请求延迟或吞吐是否改善 |

## 本教程中的三个例子

Chapter05 的量化 GEMV 在读取量化块后直接完成反量化、点积和归约，避免先生成完整浮点权重矩阵。Chapter04 的在线 Attention 维护行最大值、指数和与加权输出，避免保存完整概率矩阵。SmolVLM Packed Prefill 则展示一个反例：Linear 与 FFN 已处理打包词元行，但首版逐词元启动 Attention，使 Score、Softmax 和 Value 各出现 `12096` 次。改为按请求执行多查询 Attention 后降到 `960` 次，端到端仍因 Q8_0 GEMV 和行重排回退约 `7.7%`～`11.7%`。

第三个例子说明，减少一组计算核启动只能证明局部结构改善，不能直接证明默认路径应该切换。

## 建立可保留的融合实现

按照下面的顺序建设和验收：

1. 保留未融合实现作为数值参考和回退路径。
2. 用固定小输入比较中间结果与最终输出。
3. 用 Nsight Systems 核对启动次数和时间分布。
4. 热点仍在单个计算核时，再用 Nsight Compute 检查访存、指令、占用率和线程束停顿。
5. 回到相同真实负载做配对端到端 A/B。
6. 只有正确性、保护指标和适用范围都成立时，才改变默认路径。

Chapter04 和 Chapter05 将展开 Attention 与量化计算的具体融合；Chapter08 负责形成请求与张量批次，Chapter09 负责记录剖析证据和默认路径决策。
