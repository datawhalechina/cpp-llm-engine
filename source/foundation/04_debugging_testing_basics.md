# F04 调试与测试基础

推理引擎的错误通常来自环境、构建、形状、数值或性能测量。调试时先用最小输入复现并归类，再选择日志、断言或分析工具。

## 先给失败分类

| 失败类型 | 先检查 | 常用证据 |
| --- | --- | --- |
| 环境 | driver、toolkit、模型路径 | 命令退出码、设备枚举 |
| 构建 | target、include、链接 | CMake 配置和编译日志 |
| 形状 | 秩（rank）、维度、偏移（offset） | 断言、打印形状 |
| 内存与未定义行为 | 越界、对象生命周期、整数与类型操作 | `ASan`、`UBSan` 报告 |
| 数值 | 中间 Tensor 和参考结果 | 固定输入、误差阈值 |
| 性能 | 测量方法和输入规模 | 性能基准、性能剖析 |

## 最小验证循环

```text
最小输入 -> 复现失败 -> 检查形状 -> 检查数值 -> 保留回归测试 -> 再测性能
```

测试类型按范围分开：

| 类型 | 适合验证 | 例子 |
| --- | --- | --- |
| 单元测试 | 一个函数或对象 | `Tensor::reshape` |
| 集成测试 | 多个 target 的接口 | loader + metadata |
| 回归测试 | 已修复的错误 | 错误 shape、取消路径 |
| 性能基准 | 吞吐和延迟 | CPU 矩阵乘、解码步 |

## 最小示例

```cpp
int safe_read(const std::vector<int>& values, std::size_t index) {
  assert(index < values.size());
  return values[index];
}
```

测试至少覆盖一个正常输入和一个失败输入；失败案例保留下来，避免后续重构重新引入同一错误。

运行时错误检测器（Sanitizer）通过编译器插桩，在测试执行时发现普通断言不容易覆盖的底层错误。地址检测器（AddressSanitizer，`ASan`）重点检查越界、释放后使用和部分内存泄漏；未定义行为检测器（UndefinedBehaviorSanitizer，`UBSan`）重点检查整数溢出、错误移位、未对齐访问等未定义行为。它们会增加运行时间和内存占用，适合正确性检查，不用于性能测量。

## 验证失败后的状态

推理服务常在“已经取得部分资源”后失败。例如缓存已经预留物理块，第一层 K/V 已写入，但后续设备操作返回错误。测试此类路径时，需要在指定阶段注入故障，并同时检查四类结果：

| 检查项 | 要回答的问题 |
| --- | --- |
| 错误传播 | 调用者是否收到原始失败，而不是继续执行 |
| 请求终态 | 请求是否进入失败或取消终态，且只完成一次 |
| 事务状态 | 未提交的写入是否回滚，已提交数据是否保持 |
| 资源计数 | block、slot、workspace 和请求记录是否恢复 |

故障注入点应描述对象和阶段，例如 `cache.after_write`。一次性故障适合验证回滚，持续故障适合验证重复失败时资源仍然守恒。只断言“函数返回失败”不够，因为数据污染和资源泄漏可能留到下一次请求才出现。
