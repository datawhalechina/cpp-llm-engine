# Tutorial Writing 教程写作与页面模板

教程页面默认先于源码被阅读。文字必须先用具体输入、输出、数据变化和失败现象讲清原理，再映射到实现和验证；文件名和类名不能代替首次解释。

## 1. 内容分层

| 位置 | 读者问题 | 保存内容 |
| --- | --- | --- |
| 根 README、USAGE | 从哪里开始 | 定位、环境、最短入口和学习路线 |
| Foundation | 缺少哪些前置能力 | C++、CMake、测试、CPU/CUDA 基础与练习 |
| Chapter00–10 正文 | 为什么这样设计、代码怎样工作 | 原理、数据流、设计取舍、源码映射和验证 |
| `code/<chapter>/README.md` | 按什么顺序读代码 | 架构、对象、阅读顺序、命令和测试证据 |
| guides | 怎样组合稳定章节 | 可变学习计划和阶段任务 |
| reference | 到哪里查统一定义 | 术语、公式、实验和成熟框架坐标 |
| maintenance | 怎样长期保持一致 | 定位、写作、教学资产和代码质量规则 |

章节正文不得引用某套学习计划的 Task 编号、当前完成率或建设优先级。计划可以引用稳定章节，调整计划不要求改写正文。

## 2. 模板适用范围

所有学习内容共享同一组质量标准：先解释具体问题，再连接代码；已实现声明能定位到测试或实验；失败路径、资源状态和明确未完成能力不被省略。页面结构按内容职责选择，不要求目录和标题完全相同。

| 内容类型 | 主要任务 | 结构要求 |
| --- | --- | --- |
| Foundation | 按需补齐 C++、构建、测试和 CUDA 前置能力 | 能力选择、正文与练习映射、单题验收；不强制 A/B/G/M、真实模型或框架对照 |
| Chapter00 | 建立外部真实推理基线 | 环境、外部工具、模型、首次推理和排错；框架入口集中在 llama.cpp 基线，不复制自研章节结构 |
| Chapter01–02 | 固定输入、加载、Tensor 与 Storage 契约 | 使用章节导读、正文和代码 README 模板；真实模型、GPU 或服务验收只在确有实现时加入 |
| Chapter03–10 | 逐步构建执行、状态、调度、证据和服务 | 完整使用章节导读、正文、代码 README、框架坐标和分层验证规则 |

因此 Chapter00–02 可以使用与后续章节相同的审核问题，但“不适用”是允许的审核结论，不能为追求版式一致而补造 GPU、真实模型、服务或性能内容。

## 3. 章节导读

`intro.md` 默认只使用三个二级标题：

1. `本章导读`：说明上游输入、本章处理、输出和在引擎中的位置。
2. `开始学习`：给出 3–7 个正文页面的行动顺序、源码入口和每步观察对象。
3. `验证与下一步`：列出命令、成功条件、本章新增能力和下一章交接。

导读只保留一张主图，同时表达章节位置和内容概要。A/B/G/M 路线写在导读中，不为路线拆分重复正文：A 是小尺寸教学闭环，B 是真实 CPU 路径，G 是 GPU 后端扩展，M 是多模态输入扩展。没有真实代码或证据时，只能标为扩展坐标。

正文与验证已经收口到 `intro.md`，不再新建独立 `summary.md`。历史 summary 只保留跳转时，不复制背景、源码和结论。

## 4. 正文页面

一个页面只解决一个技术问题，默认按三个阶段展开：

1. **原理与数据变化**：从具体输入、输出、公式、shape、布局、状态或生命周期提出问题。
2. **设计与实现映射**：说明当前选择为什么能解决问题、代价是什么，再连接 C++ 对象和调用顺序。
3. **验证与下一步**：使用固定输出、失败路径、测试或实验判断结果，并说明下一页为什么需要它。

关键实现页至少回答：问题怎样出现；数据怎样变化；为什么采用当前设计；哪些代码对象实现它；学习者能观察到什么。连续/非连续布局、所有权、临时结果提交、CPU/GPU 替换点、错误恢复和资源释放不能只用“保持契约”概括。

正文开头先叙述场景，不直接堆学习目标和设计清单。列表负责收束约束、失败模式和步骤，不承担主要叙事。命令通常放到验证阶段，只有命令本身属于推导步骤时才提前。

## 5. 代码 README

`code/<chapter>/README.md` 面向已经读过正文、准备进入源码的学习者。默认使用四个二级标题：

1. `代码架构`：输入、公共请求、算子/后端/内核或状态对象、所有权、失败提交和上下游接口。
2. `阅读顺序与资产`：按理解顺序列文件、阅读重点和对应测试，不按目录字母顺序罗列。
3. `运行与验证`：给出仓库根目录命令、预期输出和 unit/component/contract/integration 证据。
4. `扩展入口`：只列真实存在的 GPU、多模态、真实模型或下一章连接点；没有则省略。

代码架构是必选内容。先用文字解释调用关系和关键设计，再放流程图；图后不补充新的关键信息。README 不重复公式推导、框架背景、维护状态或完整目录树。

## 6. 正文与源码

- 先用中文概念、公式、形状或状态变化完成解释，再给出类型名和函数名。
- 关键实现页在靠前位置链接具体源码；背景、复杂度和兼容页只保留少量入口。
- 源码入口服务阅读顺序，不把仓库目录清单伪装成学习路径。
- Python 只在能显著降低数学或控制流理解成本时作为算法镜像，不建立第二套 Runtime，也不成为默认 CMake/CTest 依赖。
- Python 生成的 golden 记录 seed、shape、dtype、容差和来源；C++ 默认测试读取固定 fixture，不现场生成答案。

源码文件头放在第一条 `#include` 或 `#pragma once` 前，保持 3–5 行。根据文件类型说明对象或场景、输入输出或行为、关键限制和验证入口，不强制套用“职责/契约”标签。中文概念优先，代码类型和稳定专名保留英文；行内注释只解释布局、生命周期、溢出和失败恢复，不逐行翻译代码。

## 7. 正文与练习

正文回答“为什么这样做、代码怎样工作”；练习回答“学习者需要修改什么、什么结果算完成”。正文只保留练习入口，不复制题目清单、提示和验收表。练习集合 README 管理目录、顺序和运行方式，单题 README 只描述当前题目。

## 8. 语言与信息密度

- 中文正文优先；API、命令、文件名、CUDA、cuBLAS、KV Cache 等稳定专名保留原文，首次出现说明作用。
- 代码名用于连接实现，不作为理解概念的前提。
- 标题表达问题、动作或对象，不使用“概览、进一步理解、这一层、这一页”等空泛指代。
- 删除重复分类、连续否定式边界说明、复述式总结和维护者口吻；保留必要公式、数据流和设计取舍。
- “已实现”必须有当前命令和证据；计划能力、外部参照和真实可运行能力明确区分。
- 图表或表格前写完必要解释，图表后不追加新的关键信息。

## 9. 提交前检查

- 页面解决一个明确问题，标题层级不为单句内容增加小节。
- 原理、设计、源码和验证按学习顺序出现。
- 章节导读、正文、代码 README 没有重复维护同一张资产表或命令说明。
- 源码链接、图片、命令和预期输出与当前实现一致。
- 学习者内容不含 P0/P1、建设优先级、迁移步骤或维护记录。
- 执行文档结构、风格、引用和链接检查，并用 `git diff --check` 检查空白。
