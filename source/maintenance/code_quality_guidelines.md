# Code Quality 代码质量与审核规则

本规则适用于 `code/` 下的 C++、CUDA、测试和构建代码。审核需要确认四件事：结果符合公式和契约，失败保留有效状态，接口写明隐式成本，期望结果来自被测实现之外。

## 1. 审核顺序

1. 从正文提取输入、输出、数据变化和失败行为，核对职责边界。
2. 检查接口的 shape、dtype、布局、设备、生命周期、错误方式和资源状态。
3. 沿入口检查索引、状态变化、申请释放、失败恢复和并发交错。
4. 核对测试期望值的来源，并确认示例、脚本和 CMake 实际执行声明的 target。
5. 运行适用门禁，文档和图片只保留已有证据支持的能力声明。

审核顺序固定为职责、接口、行为、证据、命名与格式。

## 2. 正确性与数据安全

- 公式、shape、stride、offset、索引和状态转换与正文一致。
- 元素数、字节数和索引计算在运算前检查整数溢出。
- 浮点测试按误差选择绝对或相对容差；只有可精确表示的结果使用精确相等。
- SIMD、量化、融合和 CUDA 与独立 reference 或固定 golden 比较。
- 指针解引用前检查空值、容量、设备和布局；调用方负责的前置条件写入公共接口。
- CPU、CUDA 和 pinned host memory 的转换由显式接口完成，并覆盖复制方向、同步点和失败路径。

## 3. 所有权、资源与并发

- 拥有资源的对象使用 RAII；View、引用和非拥有指针明确生命周期。
- stream、event、handle、workspace、KV block 和请求槽位在正常、取消和失败路径成对释放。
- 写入前完成校验；要求失败原子性时先写临时结果，成功后提交。
- 请求、缓存事务和服务生命周期只提交一次终态；重复完成或取消保持资源计数不变。
- 共享可变状态说明线程模型，并验证竞争、取消和终态交错。

## 4. 接口、职责与可读性

- 公共接口说明 shape、dtype、布局、设备、生命周期、失败行为、同步和 fallback。
- 可恢复输入、资源和设备错误返回 `Status`；便捷包装抛异常时保留原始原因。
- 复制、连续化、设备迁移、同步和 CPU fallback 进入接口说明、状态或指标，并由测试覆盖。
- 章节通过公开 target 和头文件连接，私有 `.cpp` 只由所属 target 编译。
- 两个实现共享同一契约时再提取抽象；单一实现保持直接调用链。
- 主流程可从入口连续追踪，类型和函数名指出处理对象；教学 reference 保留边界与溢出校验。
- 文件头说明职责、契约和验证入口；行内注释只解释布局、生命周期、溢出和失败恢复。

## 5. 测试与证据

| 层级 | 证明内容 | 最低要求 |
| --- | --- | --- |
| unit | 局部公式、索引或状态函数 | 固定输入、边界和失败输入 |
| component | 单章对象协作 | 公开接口、结果和失败原子性 |
| contract | 跨实现共同遵守的行为 | reference 与候选实现共用用例 |
| integration | 相邻章节真实交接 | 使用公开类型和 target |
| real_model | 权重、Tokenizer 和模型执行 | 固定模型、配置和结果 |
| e2e | 请求到终态的完整链路 | 生命周期、输出、指标和资源释放 |

一个测试块验证一个可命名行为。期望值由固定 golden、手算样例或独立 reference 产生；随机测试记录 seed、shape、dtype 和容差。CUDA 编译、设备执行和 CPU 数值对照分别记录。

## 6. 性能与路线证据

正确性通过后再 benchmark，定位瓶颈后再优化。前后结果使用相同 workload、构建类型、线程数、设备、warmup 和统计方法，并记录环境与原始数据。热路径中的分配、复制、锁、同步和设备传输必须可识别。

| 路线 | 审核重点 | 必要证据 |
| --- | --- | --- |
| A 教学闭环 | 算法和数据变化能否直接阅读 | 小尺寸输入、reference 和失败路径 |
| B 真实 CPU | 是否接入真实资产和跨章接口 | 集成测试、真实模型或固定 golden |
| G GPU | 设备资源、异步执行和 CPU 对照 | 编译、设备执行和数值对照 |
| M 多模态 | 新输入是否在 embedding 后复用 Runtime | 预处理、投影、拼接和请求生命周期 |

## 7. 模型与执行策略准入

新增模型或策略时，先定位变化层。模型差异通过 metadata、权重映射和组件策略进入公共 Tensor、Runtime、Scheduler 与 Transport。候选 backend 遵守既有接口和失败约定，并用明确状态报告能力缺口。

| 准入门 | 必须证明的内容 | 最低证据 |
| --- | --- | --- |
| Schema | architecture、shape、dtype 和必需 Tensor | 合成错误输入、真实索引、失败原子性 |
| Payload | block 布局、字节数和解码公式 | 独立 fixed golden 与参考实现对照 |
| Component | RoPE、Attention、FFN/MoE 局部语义 | 小尺寸 reference、边界和非法输入 |
| First layer | 真实权重映射、布局和组件组合 | hidden、K/V 或路由结果对照 |
| Decoder | 多层执行和 LM Head | logits 指标与 greedy token 序列 |
| Runtime | Prefill、Decode、Context 和 KV 状态 | 重置、多 Context 与失败回滚 |
| Serving | 请求生命周期和资源治理 | 同步、流式、并发、取消、超时与释放 |

能力声明写成最高已通过层级，例如“Schema”或“Runtime”。真实模型证据记录版本或 SHA256、配置、Tokenizer 输入、容差、golden 和环境；数值正确性同时检查中间结果或 logits，服务能力另检查并发与终态。

新策略保留 reference，通过相同 workload 的正确性对照后再测性能；状态型策略还需验证资源不足、部分成功、取消和重复终态。公共接口、dtype、policy 或 target 变化执行直接 owner、相邻集成和默认回归；Runtime/Serving 变化增加发布验收。发现错误、状态污染、旧路径回退或声明超前时，修复或撤回能力声明。

失败恢复测试使用 `code/testing` 的命名故障点，在指定调用次数触发一次性或持续失败。故障注入器由测试夹具持有，生产接口只暴露真实错误返回；断言同时覆盖命中次数、请求终态、缓存提交量和资源释放量。

## 8. 问题等级与两轮审核

| 等级 | 判断标准 | 处理要求 |
| --- | --- | --- |
| P0 | 错误结果、越界、泄漏、数据竞争，或测试误判 | 合并前修复并增加回归 |
| P1 | 生命周期不安全、职责错误、绕过公共接口、文档与实现不一致 | 当前批次修复或撤回声明 |
| P2 | 覆盖不足、失败定位困难、重复实现或隐式行为 | 记录位置、owner 和验收标准 |
| P3 | 命名、注释、局部结构和格式问题 | 当前修改范围允许时修复 |

章节审核分两轮：建设审核冻结标准、形成问题清单并修正；冷启动验收重新从文档声明反查接口、相邻章节、失败输入、资源释放和证据。设计或实现发生变化后，由第二轮给出最终结论。

收敛要求：P0/P1 数量为零；P2 已修复或登记 owner 与验收标准；文档、图片、代码 README、接口和测试使用同一概念；模型、CUDA、网络和性能验证均记录执行状态。

## 9. 自动门禁

自动门禁负责可重复检查，人工审核负责职责、生命周期和期望值来源。CPU 章节可运行统一局部门禁：

```bash
npm run test:cpp-quality -- code/chapter04_attention \
  '^(chapter04_attention_test|chapter02_tensor_attention_integration_test)$'

npm run test:fault-injection
```

脚本默认运行严格警告和 UBSan；环境支持时可增加 `CPP_LLM_ENABLE_ASAN=1`。CUDA 仍需单独记录 `nvcc` 编译、设备执行和 CPU 对照。完整测试注册和证据层级见 [`code/testing/README.md`](../../code/testing/README.md)。

通过条件：局部质量检查、默认回归和受影响发布验收通过，文档、接口、实现与证据一致。过程记录留在本地，只有长期规则进入本文件。
