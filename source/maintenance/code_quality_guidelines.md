# Code Quality 代码质量与审核规则

本规则定义 `code/` 下 C++、CUDA、测试和构建代码的质量要求与审核方法。审核最终回答四个问题：结果是否正确；失败是否安全；接口是否诚实；证据是否独立。

## 1. 审核顺序

1. 从正文提取已承诺的输入、输出、数据变化和失败行为。
2. 检查公共头文件中的 shape、dtype、布局、所有权、生命周期和错误方式。
3. 沿入口检查索引、状态变化、资源申请释放和失败后的对象状态。
4. 检查正常、失败、边界、状态和跨章测试是否提供独立证据。
5. 检查示例、脚本和 CMake 是否实际构建并执行声明的 target。
6. 运行局部测试、严格警告、适用的 Sanitizer、默认回归和发布契约。
7. 回到正文与图片，删除代码或测试不能证明的能力声明。

先审职责和接口，再审局部命名与格式，避免在错误架构上优化代码风格。

## 2. 正确性与数据安全

- 公式、shape、stride、offset、索引和状态转换与正文一致。
- 元素数、字节数和索引计算在运算前检查整数溢出。
- 浮点测试按误差选择绝对或相对容差；只有可精确表示的小整数结果使用精确相等。
- reference 保持直接可读；SIMD、量化、融合和 CUDA 与独立 reference 或固定 golden 比较。
- 指针在解引用前检查可验证的空值、容量、设备和布局条件；无法由原始指针验证的前置条件写入公共接口。
- CPU、CUDA 和 pinned host memory 不隐式互换。

## 3. 所有权、资源与并发

- 拥有资源的对象使用 RAII；View、引用和非拥有指针明确生命周期，能由类型系统拒绝临时对象时不只依赖注释。
- stream、event、handle、workspace、KV block 和请求槽位在正常、取消和失败路径成对释放。
- 写入前完成校验；要求失败原子性时先写临时结果，成功后提交。
- 请求、缓存事务和服务生命周期只能进入一个终态，重复完成或取消不能重复释放资源。
- 共享可变状态说明线程模型，并验证竞争、取消和终态交错。

## 4. 接口与章节职责

- 公共接口明确 shape、dtype、布局、设备、所有权、生命周期、失败行为以及复制、同步和 fallback。
- 可恢复输入、资源和设备错误返回 `Status`；便捷包装可以抛异常，但不能丢失原因。
- 禁止静默复制、连续化、设备迁移、同步和 CPU fallback。
- 章节只拥有当前阶段对象，通过公开 target 和头文件连接相邻章节，不包含其他章节私有 `.cpp`。
- 抽象对应真实变化点，例如 CPU/CUDA 后端、调度策略或 transport；单一实现不提前叠加多层 Factory/Manager。
- 教学包装与真实主线明确命名，不能把局部 `Matrix` 误认为全局 Tensor。

## 5. 教学可读性与注释

- 主流程能沿入口函数阅读，算法步骤不被无关模板和抽象打散。
- 类型和函数使用具体名称，避免无法说明所管理对象的 `Manager`、`Helper`、`Processor`。
- 教学 reference 可以朴素，但不能省略影响正确性和安全性的校验。
- 文件头用 3–5 行说明对象或场景、输入输出或行为、关键限制和验证入口。
- 中文概念优先，代码类型和稳定专名保留英文；行内注释解释布局、生命周期、溢出和失败恢复，不逐行翻译代码。

## 6. 测试与证据

| 层级 | 证明内容 | 最低要求 |
| --- | --- | --- |
| unit | 局部公式、索引或状态函数 | 固定输入、边界和失败输入 |
| component | 单章对象协作 | 公开接口、结果和失败原子性 |
| contract | 跨实现共同遵守的行为 | reference 与候选实现共用用例 |
| integration | 相邻章节真实交接 | 使用公开类型和 target |
| real_model | 权重、Tokenizer 和模型执行 | 固定模型、配置和结果 |
| e2e | 请求到终态的完整链路 | 生命周期、输出、指标和资源释放 |

一个测试块验证一个可命名行为。测试不能调用被测实现生成期望值；随机测试记录 seed、shape、dtype 和容差。CUDA 分别记录编译、真实设备执行和数值对照，三者不能互相替代。

## 7. 性能质量

- 正确性通过后再 benchmark，定位瓶颈后再优化。
- 热路径中的分配、复制、锁、同步和设备传输必须可识别。
- 优化前后使用相同 workload、构建类型、线程数、设备、warmup 和统计方法。
- 优化不改变公开结果、错误行为和资源回收规则。
- 性能记录包含环境和原始数据；单次耗时不能支持结论。

## 8. A/B/G/M 审核重点

| 路线 | 主要问题 | 必要证据 |
| --- | --- | --- |
| A 教学闭环 | 算法和数据变化能否直接阅读 | 小尺寸输入、reference 数值和失败路径 |
| B 真实 CPU | 是否接入真实资产和跨章接口 | 集成测试、真实模型或固定 golden |
| G GPU | 设备资源、异步执行和 CPU 对照 | 编译、真实设备执行和数值对照分别记录 |
| M 多模态 | 新输入是否在 embedding 后复用 Runtime | 预处理、投影、拼接和请求生命周期证据 |

## 9. 问题等级

| 等级 | 判断标准 | 处理要求 |
| --- | --- | --- |
| P0 | 错误结果、越界、泄漏、数据竞争，或测试把错误实现判为通过 | 合并前修复并增加回归 |
| P1 | 生命周期不安全、章节职责错误、绕过公共接口、文档与实现不一致 | 当前批次修复或撤回能力声明 |
| P2 | 测试覆盖不足、失败定位困难、重复实现、隐式行为未说明 | 记录位置、owner 和验收标准 |
| P3 | 命名、注释、局部结构和格式问题 | 不扩大范围时修复 |

结论先列 P0/P1，再列 P2/P3。没有发现问题时，也要记录未执行的真实模型、CUDA、网络和性能验证。

## 10. 自动门禁与通过条件

编译警告发现未使用对象、危险转换和遮蔽；ASan/UBSan 发现部分越界和未定义行为；CTest 证明已编写行为；默认回归检查跨模块退化；Release 契约检查 owner、label 和全新构建。它们都不能替代职责、生命周期和证据独立性的人工审核。

CPU CMake 目录使用统一局部门禁；第二个参数可限制 CTest 名称，避免父章节带入的子目录测试扩大审核范围：

```bash
npm run test:cpp-quality -- code/chapter04_attention \
  '^(chapter04_attention_test|chapter02_tensor_attention_integration_test)$'
```

该脚本适用于 GCC/Clang 的 CPU 构建，默认运行严格警告和 UBSan。确认执行环境支持 ASan 时，可增加 `CPP_LLM_ENABLE_ASAN=1`；某些 ptrace 或容器环境无法稳定运行 ASan，不能把运行器等待误记为代码通过或失败。CUDA 仍需分别记录 `nvcc` 编译、真实设备执行和 CPU 数值对照，不能用本脚本代替。

代码质量通过要求：没有未处理 P0/P1；P2 有明确 owner 和验收标准；局部测试、严格警告和适用 Sanitizer 通过；默认回归与受影响发布契约通过；文档、接口、实现和证据一致；未执行的外部验证被明确记录。

审核记录只需保存范围、已执行验证、未执行验证、按等级排列的发现和最终结论。单章过程记录属于本地自留；只有跨章节长期规则进入本文件。
