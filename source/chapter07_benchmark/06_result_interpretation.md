# 07.6 从结果作出工程决定

基准结果只有和正确性、基线及测量条件放在一起才有意义。本节使用统一顺序检查结果，并避免用脱离数据类型和计算阶段的通用误差阈值。

## 先判断结果是否可比较

按以下顺序读取两组结果：

1. `correctness`、完成请求数和生成词元数是否一致。
2. 模型、输入输出长度、请求数和执行方式是否一致。
3. 硬件、构建、预热、迭代和计时区间是否一致。
4. 性能差异是否超过重复运行的自然波动。

正确性失败时停止性能比较。比较量化误差时，阈值应来自对应格式、算子和浮点参考路径；比较服务输出时，应同时检查固定词元、终态和资源释放。`cosine_similarity > 0.99` 或 `MAE < 1e-4` 不能作为所有场景的统一标准。

## 将差异映射到决定

| 观察结果 | 当前结论 | 下一步 |
| --- | --- | --- |
| 正确性通过，差异大于波动 | 存在可重复性能变化 | 进入 Chapter08 定位原因，再决定保留 |
| 正确性通过，差异落在波动内 | 尚无可证明收益 | 增加样本或改善测量方法 |
| 正确性通过，但工作负载不同 | 两组结果不可直接比较 | 统一条件后重跑 |
| 正确性失败 | 性能结果无效 | 修复或回滚后重新建立基线 |
| 资源占用明显增加 | 可能用空间换时间 | 同时报告内存和吞吐，再按目标取舍 |

最小实验记录应包含命令与提交、模型与负载、机器与构建、正确性证据、原始结果文件和决定。不要只摘录一行吞吐数字，也不要把教学 Runtime 的结果和真实 HTTP 服务结果放在同一列直接比较。

```markdown
## 实验记录

- 提交与命令：...
- 模型与负载：...
- 机器与构建：...
- 正确性：PASS / FAIL，证据为 ...
- 基线结果：...
- 实验结果：...
- 决定：保留 / 回滚 / 继续测量
```

## 验证与衔接

选择 Chapter07 的两份同类 JSON，逐项写出可比条件、正确性和最终决定。如果无法说明计时区间或环境差异，应将结论标记为“待复测”。随后进入 [`07.7 成熟框架对照`](./07_framework_comparison.md)，核对不同工具的 workload 和指标口径。
